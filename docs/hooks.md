# Guardrail hooks

With the plugin enabled, Claude Code loads [`hooks/hooks.json`](../hooks/hooks.json) automatically. Every hook runs one dispatcher, [`hooks/guardian-hook.mjs`](../hooks/guardian-hook.mjs), which imports only Node built-ins and the pre-compiled detectors in `mcp/dist/` — no `npm install`, no native module.

Two rules hold for all of them:

- **Fail open.** Any error inside a hook exits 0 with no output. A guardrail that breaks must not break your session. `GUARDIAN_HOOKS_DEBUG=1` prints what went wrong on stderr. It is not silent, though: when the shell guard, the secret scan, package vetting or the settings guard cannot be loaded (a missing or damaged `mcp/dist`), SessionStart says which ones are off for the session.
- **Only what just happened.** A hook assesses the text just written or the command about to run — it never scans the repository. It does read a little around it: SessionStart runs `git status` and checks `.guardian/`, and the install hook reads registry configuration (`.npmrc`, `pip.conf`, `package.json` workspaces, … — listed below). The authoritative scans stay in the MCP tools (`scan_secrets`, `vet_packages`, …).

Each hook has a 15 s timeout in `hooks.json`.

## What runs when

| Event | Matcher | What it does | Default |
| --- | --- | --- | --- |
| `SessionStart` | — | Briefs the agent: plugin version, branch, uncommitted changes, whether the project has a `.guardian/` directory and when the database last changed — and, when the project's hook config asked to loosen a guardrail, that it was ignored. | on |
| `PostToolUse` | `Write`, `Edit`, `MultiEdit`, `NotebookEdit` | Scans the inserted text for hard-coded secrets (medium confidence and up) and adds a warning with a **redacted** preview. A long line — a one-line JSON file, a minified bundle — is read to its end, in overlapping 16 KB windows. | warn |
| `PreToolUse` | `Bash`, `PowerShell` | Assesses the command: **denies** catastrophic ones, warns on risky ones, then vets any package it would install. | deny catastrophic |
| `PreToolUse` | `Write`, `Edit`, `MultiEdit` | **Denies** any edit of the guard's own configuration, and an edit of Claude Code's `.claude/settings*.json` that would switch the hooks off (below). | always — unless every hook is switched off at user level |
| `PreToolUse` | `Write`, `Edit`, `MultiEdit`, `NotebookEdit` | Denies writing a high-confidence provider token (AWS, GitHub, Stripe, …). | off — opt in with `"secrets": { "block": true }` |

## The shell guard

The same detector serves `Bash` and `PowerShell` and the CLI's `check --bash`. It splits a command line into statements and also reads text that is fed to a shell (`bash <<EOF … EOF`, `echo '…' | sh`); a heredoc handed to a non-shell command (`git commit -F - <<EOF`) stays inert.

From the **PowerShell tool** the command is read twice — as a POSIX shell quotes it, and as PowerShell does (a backslash is literal, a backtick escapes, `''` inside `'…'` and `""` inside `"…"` are one quote, typographic quotes are quotes, a here-string `@'…'@` is one literal, `<# … #>` is a comment, after `--%` the rest of the line — up to a `|` — goes to the program unparsed, and the commands in a script block, `ForEach-Object { … }` included, are assessed like any other) — and the more severe verdict stands. Read the POSIX way alone, an ordinary Windows path ending in `\"` escapes its closing quote and swallows the rest of the line: `Remove-Item "C:\Users\" -Recurse -Force` was `ok`. Program text handed to `pwsh -Command` / `-EncodedCommand` is read both ways too, from either tool. Both readings treat a `#` that starts a word as a comment to the end of the line — not one that continues a word, as after `$(…)` in bash or `=` in a PowerShell argument. `check --bash "…" --powershell` reads a command the same way.

- **Denied** (unless the block is switched off): recursive force-deletes of the filesystem root, the home directory (`~`, `$HOME`, `${HOME}` and their `/*` and `\*` forms, Git Bash's `$USERPROFILE` and `$HOMEDRIVE$HOMEPATH`, cmd's `%USERPROFILE%` and PowerShell's `$env:USERPROFILE`, and the home directory's own path — `C:\Users\<name>`, `/c/Users/<name>/`, `/home/<name>/*` — compared with the account's home, case-insensitively on Windows; a path below home only warns), Windows and Git Bash / WSL drive roots (also `%SystemDrive%`, `%HOMEDRIVE%`, and PowerShell's `\` and `\*`), `/Users`, `/System`, `C:\Windows`, `C:\Users`, `C:\Program Files`, and `--no-preserve-root`; a download run as a script, official installers included — `curl`/`wget` piped into a shell however the shell is named (`| /bin/bash`, `| env VAR=x sh -`, `| "bash"`, `| command bash`, `| exec bash`, `| sudo -u root bash`, `| source /dev/stdin`), `bash <(curl …)`, `source <(curl …)`, `. <(wget …)`, `bash <<< "$(curl …)"`, `sh -c "$(curl …)"`; the same with an interpreter reading its program from the download (`| python3 -`, bare `| node`, `| perl`, `| ruby`, `| php`, `| deno run -`, `| bun run -`, `python3 -c "$(curl …)"`, `node -e "$(curl …)"`, `python3 <(curl …)` — its options read with its own table of those that take a value, so `python3 -W ignore -` and `node --max-old-space-size 4096 <(curl …)` count; not `| python3 -c '…'`, `| python3 script.py` or `| python3 -m json.tool`, where the download is only data) and `| xargs -0 sh -c`, which makes the download the `-c` script; a file saved by `curl -o` / `-O` / `> f` or `wget` and run on the same command line (`sh f`, `bash f`, `./f`, `source f`, `python3 f`) — also after `mv` / `cp` / `install` to another name — unless a checksum or signature check of that file (`sha256sum -c`, `shasum -c`, `gpg --verify`, `cosign verify-blob`, … naming the file, its `.sha256` / `.sha256sum` / `.asc` / `.sig` / `.minisig`, or a checksum list downloaded in the same command) lies between the download and the run and the run is joined to it by `&&`; a bare command name (`kubectl version`) runs what PATH finds, so it counts only under `cmd /c`, which searches the working directory, or once the download was placed in a PATH directory in the same command (`install -m 755 tool /usr/local/bin/ && tool`) — a download run by a later, separate command is not judged at all; PowerShell `iwr | iex`, `(irm …) | iex`, `iex (irm …)`, `iex ((New-Object Net.WebClient).DownloadString(…))`, `iex "… $(irm …) …"`, `Invoke-Expression (Invoke-RestMethod …)`, a download held in a variable and handed to `iex` (`$s = irm …; iex $s`), a script block made from a download — `&([scriptblock]::Create((iwr …)))` (Microsoft's dotnet-install one-liner), `[scriptblock]::Create(…).Invoke()`, `Invoke-Command -ScriptBlock (…)`, `$ExecutionContext.InvokeCommand.InvokeScript(…)` / `.NewScriptBlock(…)` — also inside `powershell -Command "…"` or `-EncodedCommand`, and a file saved by `DownloadFile(…)`, `Invoke-WebRequest -OutFile` or `Start-BitsTransfer` and then run in the same command (`& file`, `. file`, `.\file`, `powershell -File file`, `Start-Process file`, `msiexec /i file`, `Get-Content file | iex`) — opening a downloaded document (`Start-Process readme.txt`, `ii notes.pdf`) is not running it, and a file merely named `x.iex` is no `iex`; `Format-Volume`, `Clear-Disk`; `dd`, `mkfs`, `wipefs` or `shred` on a block device; fork bombs; `chmod -R 777 /`; `find / -delete`; `mkfifo`, `mknod`, `ln`, `mklink` (also through `cmd /c`, anywhere in its command line) or PowerShell `New-Item -ItemType SymbolicLink|HardLink|Junction` when the path it creates is one of the hook configuration files, or a link at `.guardian` or `~/.config/dev-guardian` — not when that path is only a link's source; a shell write onto one of the hook configuration files, its removal, a directory moved or copied onto a configuration directory, program text on the command line that names one, a shell write of Claude Code's settings that names a key switching the hooks off, and `claude plugin disable|uninstall` of dev-guardian — see [Shell writes](#configuration). Commands inside `do … done`, `then … fi`, `else`, `{ … }`, `function f { … }`, `time { … }` and after `!` are assessed like any other, and so are the scripts handed to `bash -c`, `eval`, `iex` / `Invoke-Expression`, `npx -c` and PowerShell's `-Command` / `-EncodedCommand`, every command of a `cmd /c` line (`cmd /c rd /s /q C:\` is denied as `rd /s /q C:\` is), and the program cmd's `start` launches.
- **Warned**: force-push, `git reset --hard`, `git clean -fd`, `chmod 777`, clearing shell history, `sudo`, any other recursive force-delete, `find ~ -delete`.

The deny message never says how to switch the guard off. That takes the user-level config or `GUARDIAN_HOOKS_BASH_BLOCK=0`, and an assistant's `Write` / `Edit` of either config file — or a shell write onto it that the guard can see — is itself denied.

## Install-time package vetting

When the command installs packages by name — `npm i|install|add`, `pnpm add`, `yarn add`, `bun add|i|install`, `pip install`, `uv add`, `uv pip install`, `poetry add`, `composer require`, `dotnet add package` — or downloads one to run it — `npx`, `npm exec`, `pnpm dlx` / `pnpx`, `yarn dlx`, `bunx` / `bun x`, `uvx` / `uv tool run`, `uv tool install`, `pipx install`, `pipx run` (the package is the first word after the launcher's own options, or the value of its `-p` / `--package` / `--from` / `--spec`, plus `uvx --with`; the words after it are the program's; `npx`, `npm exec` and `bunx` of a bin the project has in `node_modules` fetch nothing and are not vetted) — the hook runs the same checks as the `vet_packages` tool, under one **3 s** network budget for the whole command line and one **8 s** deadline for everything the hook call does (`GUARDIAN_PKG_VET_DEADLINE_MS`, at most 14000, counted from the start of the call) — Claude Code kills a hook at 15 s, and the command then runs with no verdict at all. Local work — reading registry configuration, walking a workspace — happens after the network and only for a name the registry does not have, each file read and each workspace walked once per call; what the deadline leaves unchecked reads "vetting time budget exhausted" and is never reported as vetted. It looks each package up once, at most 50 packages per command — names not on the popular list first, so padding a command with popular names cannot push another past the cap (a note says how many more were not vetted) — and reads a command for installs to 512 KB (past that, no missing-name deny, and a note says so, even when the first 512 KB install nothing):

| Finding | Hook answer |
| --- | --- |
| A version that would install is **malicious** (OSV `MAL-` advisory, or npm's `0.0.x-security` placeholder) | **deny**, in every command shape; the message says to ask the user to install it themselves |
| The name does **not exist** on the public registry | **deny** only when the whole command, comments stripped, is ONE plain install statement — a bare tool name (no `.venv/bin/pip`, `sudo`, `env`, `VAR=x`), no `&&`, `\|\|`, `;`, pipes, `&`, subshells, `$(…)`, backticks, variables, redirections, unquoted commas or `'…''…'`, and only flags from a small per-tool allowlist that cannot change where a package resolves from (not `composer --no-update` / `--no-install` or `dotnet --no-restore`, which defer the lookup) — and nothing below explains the 404. Otherwise a warning: "not found on the public registry — if it is private or local, ignore this". |
| Published less than 72 h ago, npm install scripts, typosquat suspicion, an unpublished exact version | warning |
| Known vulnerabilities | warning, only for an exact version pin (for a range the installed version is unknown) |
| A check could not run (offline, timeout, HTTP error, rate limit, `GUARDIAN_OFFLINE=1`) | one line saying the package was **not** verified; the command runs |
| Every package clean, or nothing installed by name | silent, and no network request at all |

A missing-name deny carries its own escape hatch, named for the tool: re-run the install with an explicit `--registry <url>` (npm, `npx`, pnpm, bun), `--index-url <url>` (pip, `uv pip`, pipx), `--index <url>` (`uv add`, `uvx`, `uv tool`) or `--source` (poetry, dotnet), or prefix the command with `GUARDIAN_PKG_VET=0` — from the PowerShell tool, `$env:GUARDIAN_PKG_VET = '0'` first in the same command. Composer and Yarn Berry have no registry flag, so theirs names only the prefix. Either way the command is no longer one plain install statement; the hook's own switch is untouched, and a malicious version is still denied. A malicious-package deny has no escape hatch.

From the **PowerShell tool** the command is also read the way PowerShell reads it: `npm i a,b` hands npm two packages, a backtick at the end of a line continues it, a backslash before a closing `"` is literal, `''` inside `'…'` is one quote, and a no-break space separates words. A package only that reading finds can be denied as malicious, never as missing.

What counts as "something explains the 404" — the hook reads files and environment only, never the network, for this:

- **npm, pnpm, yarn, bun**: `registry=` or `@scope:registry=` in the project `.npmrc`, the user npmrc (`NPM_CONFIG_USERCONFIG` or `~/.npmrc`), npm's global npmrc (`npm_config_globalconfig`, `npm_config_prefix`, `%APPDATA%\npm\etc\npmrc` or `<node prefix>/etc/npmrc`) and pnpm's global rc; yarn's `.yarnrc.yml` `npmRegistryServer` / `npmScopes` — in every directory from the project up to the filesystem root, as Yarn Berry reads it — and classic `.yarnrc`; bun's `bunfig.toml` (project or `~/.bunfig.toml`); an npmjs auth token when the name is scoped (a private scoped package answers 404 anonymously); a workspace package (`package.json` `workspaces`, `pnpm-workspace.yaml`) — a workspace is read to 3000 directories, and one larger than that, or cut short by the deadline, leaves a name it did not reach unknown, never absent.
- **pip, uv, poetry**: `pip.conf` / `pip.ini` (user, the environment's prefix — `VIRTUAL_ENV` or `CONDA_PREFIX` — `PIP_CONFIG_FILE`, `/etc/pip.conf`, `/etc/xdg/pip/pip.conf`, `XDG_CONFIG_DIRS`, `%ProgramData%\pip\pip.ini`, macOS `~/Library/Application Support/pip` and `/Library/Application Support/pip`); `uv.toml` (`UV_CONFIG_FILE`, `~/.config/uv`, `%APPDATA%\uv`, `/etc/uv`, the project); `[[tool.uv.index]]`, `[[tool.poetry.source]]`, `[[tool.pdm.source]]` or a `[tool.uv]` index in `pyproject.toml`; uv workspace members and `[tool.uv.sources]`.
- **Composer**: a `repositories` entry in `composer.json` or the user's global `config.json`.
- **NuGet**: any `nuget.config` from the project up to the filesystem root, the user-level one, every `*.config` in the extra user directories (`%APPDATA%\NuGet\config`, `~/.nuget/config`, `~/.config/NuGet/config`) and the machine-wide ones (`%ProgramFiles(x86)%\NuGet\Config`, `/etc/opt/NuGet/Config`, macOS `/Library/Application Support/NuGet/Config`), with a source that is not nuget.org — except that a machine-wide config's local-folder source (Visual Studio's `Microsoft.VisualStudio.Offline.config` is one on every VS machine) counts only for a package that folder holds (`<id>/` or `<id>.<version>.nupkg`, the id ending where a NuGet version begins — `Foo.2FA.1.0.0.nupkg` holds `Foo.2FA`, not `Foo`; a file name that splits more than one way counts for each id, so `foo.2.1.0.0.nupkg` holds `foo`, `foo.2` and `foo.2.1`).
- **The hook's environment**, case-insensitively: `npm_config_*registry*`, `YARN_NPM_REGISTRY_SERVER`, `YARN_REGISTRY`, `BUN_CONFIG_REGISTRY`, `PIP_*INDEX*`, `UV_*INDEX*`, and for NuGet only a variable that names a source, feed or configuration file (`NUGET_*SOURCE*`, `NUGET_*FEED*`, `NUGET_*CONFIG*`, `NUGET_FALLBACK_PACKAGES`) or a source's credentials (`NuGetPackageSourceCredentials_<name>`) — not `NUGET_PACKAGES` or `NUGET_XMLDOC_MODE`.
- **The command line**: any non-public `--registry`, `-i`, `--index-url`, `--source`.

These files are read like the hook configuration (below): a file reached through a link to a network or device path is not opened. A configuration that is there but could not be read — that link, a loop, a directory or FIFO where the file belongs, a file over 1 MiB, no permission — is **unknown**, never absent: it may name a private registry, so a missing name warns — "registry configuration at … could not be read — possibly a private registry", or, for a workspace's `package.json` / `pyproject.toml` or a directory that could not be listed, a message naming that — instead of being denied. A malicious version is still denied.

A registry that *is* the public one (`registry.npmjs.org`, `pypi.org/simple`, `api.nuget.org`) is not custom. Paths, tarballs, URLs, git specs (`git@host:repo` included), `file:` / `workspace:` specs, requirement files and flag values are never looked up; a bare `npm install` vets nothing.

The network hosts involved are listed in [SECURITY.md](../SECURITY.md).

## Configuration

The project is the directory Claude Code names in `CLAUDE_PROJECT_DIR`; without it, the nearest ancestor of the session's working directory that holds `.guardian` or `.git` — never the home directory or one of its ancestors, nor the temp directory itself, where a stray `.guardian` would otherwise become every unmarked project's configuration; failing both, the working directory itself. The project files below are read from there, and paths are made relative to it, wherever the session has `cd`-ed to — from `<project>/packages/api` the project's configuration applies, and a `Write` of `<project>/.guardian/hooks-allowlist.json` is denied as it is from `<project>`. A `.guardian/hooks*.json` at any depth under the project (or under the working directory) is guarded the same way. Every guarded path — these files and Claude Code's settings — is compared as the filesystem opens it: on Windows without an NTFS stream suffix (`hooks.config.json::$DATA` writes the file itself; `:name` and `:name:$DATA` are streams of it) or trailing dots and spaces (`hooks.config.json.`, `.guardian.\…`), and everywhere through an 8.3 short name (`HOOKSC~1.JSO`) or a link, when the path or a directory above it exists. The shell guard drops the same Windows suffixes from the paths a command writes.

| Where | Who may write it | What it can do |
| --- | --- | --- |
| `.guardian/hooks.config.json` (project) | the user — an assistant's `Write` / `Edit` / `MultiEdit` is denied, and so is a shell write the guard can see (below) | only what makes the guard stricter or is advisory: `enabled: true`, `bash.block: true`, `bash.warn: true`, `secrets.block`, `secrets.warn`, `sessionStart`, `ignorePaths`. `"enabled": false`, `"bash": { "block": false }` and `"bash": { "warn": false }` here are **ignored**, and SessionStart says so; there is no project-level switch for package vetting. |
| `~/.config/dev-guardian/hooks.json` (user) | the user — an assistant's `Write` / `Edit` / `MultiEdit` is denied, and so is a shell write the guard can see (below) | every key, winning over the project file: `"enabled": false` turns every hook off, `"bash": { "block": false }` turns the shell block into a warning |
| `.guardian/hooks-allowlist.json` (project) | the user — an assistant's `Write` / `Edit` / `MultiEdit` is denied, and so is a shell write the guard can see (below) | substrings that silence a secret warning (and exempt a match from the opt-in secret block when the project itself enabled it): a JSON array, or `{ "secrets": [...] }`. Advisory, like `secrets.warn`. |
| `GUARDIAN_HOOKS=off` | environment | disables every hook |
| `GUARDIAN_HOOKS_BASH_BLOCK=0` / `1` | environment | forces the shell block off or on, over both files |
| `GUARDIAN_PKG_VET=0` | environment | disables package vetting only |
| `GUARDIAN_PKG_VET_DEADLINE_MS` | environment | package vetting's deadline for one hook call, in ms from its start (default 8000, at most 14000) |

`ignorePaths` defaults to `/test/fixtures/`, `eval-vuln-fixture`, `/.guardian/` and `__fixtures__`, matched against the path relative to the project. The plugin's own directory is always skipped. The user-level `ignorePaths`, when set, replaces the project's. A project's `ignorePaths` narrows the secret **warning** only: it never exempts a path from a `secrets.block: true` set in the user-level config, which honours the user's own `ignorePaths` or the defaults. (A block the project itself enabled may be narrowed by the same project's list.) The project's `.guardian/hooks-allowlist.json` follows the same rule: it silences the warning, and it exempts a match from the block only when the project itself enabled that block — never from one the user enabled.

**How the configuration files are read.** Each one — the project config, the allowlist and the user-level config — goes through two checks, and a file that fails either is not read, counts as absent (the protective defaults), and is named by SessionStart; a file that is not valid JSON is named too.

1. **Before anything is opened**, every path component below the project directory (for the two project files) or the home directory (for the user-level file) is examined with `lstat` and `readlink`, which never follow a link and never touch its target. If a link on the way — the file itself, `.guardian`, `.config`, `dev-guardian`, or any local link one of them leads to — points at a UNC or device path (`\\host\share`, `//host/share`, `\\?\…`, `\\.\…`), the file is refused. Opening such a link can wait on the network for minutes (≈136 s was measured on Windows for an unreachable host), far past the hook's 15 s.
2. **Then the file is opened** (a link is followed; on Linux and macOS with `O_NONBLOCK`, so a FIFO opens at once instead of waiting for a writer), and what was OPENED is checked with `fstat`: only a regular file of at most 64 KiB is read, and no more than 64 KiB + 1 bytes are read from it, so a file that grows after the check is refused too. A FIFO, a link to `/dev/zero`, a Windows link to a named pipe (which `stat`s as an empty regular file), a larger file or a file this account may not read is refused on its descriptor and closed unread; a directory is refused too (Windows will not open one at all). Because these checks apply to the open descriptor rather than to the path, swapping the path for a FIFO between two checks changes nothing. A leading UTF-8 byte-order mark is stripped.

A FIFO there used to hang the hook until Claude Code killed it at 15 s, after which the tool call ran unguarded. **Not covered:** the project and home directories themselves and their ancestors (the user's own layout), and a path the operating system redirects to the network without a link — a mapped drive letter, a DFS namespace, an NFS or SMB mount — which is opened like any local path. The install hook reads registry configuration (`.npmrc`, `package.json`, `pip.conf`, `nuget.config`, …) through both checks too, capped at 1 MiB: the walk runs below the project for a file in it, from the file's own directory for one in a parent of the project, below the home directory for a user file and from the filesystem root for a system file — never over the project or home directory themselves or their parents. A refused file counts as possibly naming a private registry (above).

**Shell writes.** The shell guard judges what a command does to the three files, command by command — never their content, so reading them (`cat`, `cp` from them, `sed -n`, `grep`) stays allowed:

- **writing one** — a redirection (`>`, `>>`, `>|`, `N>`, `&>`), `tee`, `sed -i`, `perl -pi` / `ruby -pi`, `sort -o`, `truncate`, `sponge`, `shred`, `dd of=`, `curl -o`, `wget -O`, `cp` / `mv` / `install` / `rsync` onto it (or into its directory under its name, a glob that can name it included), a rename onto it, PowerShell `Set-Content`, `Add-Content`, `Clear-Content`, `Out-File`, `Tee-Object`, `New-Item -ItemType File`, `Copy-Item` / `Move-Item` / `Rename-Item`, `[IO.File]::WriteAllText` and the other `[IO.File]::` writes, and cmd `copy` / `move` / `ren` / `>`;
- **removing one** — `rm`, `unlink`, `del`, `erase`, `Remove-Item`, `[IO.File]::Delete`, a `mv` or rename that moves it away — and removing `~/.config/dev-guardian` itself;
- **replacing a configuration directory** — a directory moved or copied onto `.guardian` or `~/.config/dev-guardian` (`mv`, `cp -r` / `-a`, `rsync -a`, `Copy-Item -Recurse`, `Move-Item`, `xcopy`, `robocopy`), which becomes the directory when it did not exist.

A relative path is resolved against the `cd`, `pushd` or `Set-Location` earlier in the same command (`cd ~/.config/dev-guardian && echo … > hooks.json`), and every command of a quoted `cmd /c "…"` line is judged the same way, its `cd /d` and `>` included. Scripts a command hands a shell (`bash -c`, `eval`, `pwsh -Command`, `-EncodedCommand`) are judged as commands. Program text on the command line — `node -e`, `tsx -e`, `ts-node -e`, `python -c`, `perl -e`, `ruby -e`, `php -r`, `deno eval`, `pwsh -Command`, also behind `npx`, `bunx`, `pnpm dlx` / `exec`, `npm exec`, `yarn dlx` / `exec`, `bun x`, `uv run` and cmd's `start`, and a program fed to `python` / `node` through a heredoc or `echo … |` — cannot be judged that way, so it is denied when one of its string literals names a hook configuration path at all, reading or writing (reading one needs no program): a literal ending in the path, or the parts of one (`join(home, '.config', 'dev-guardian', 'hooks.json')`); a sentence that merely mentions it is not.

**Claude Code's own settings.** A `.claude/settings.json` or `.claude/settings.local.json` (project or user level) — and, when Claude Code runs with `CLAUDE_CONFIG_DIR`, the `settings.json` / `settings.local.json` directly in that directory, which are then the user's settings — with `"disableAllHooks": true`, an `env` block setting `GUARDIAN_HOOKS=off`, `GUARDIAN_HOOKS_BASH_BLOCK=0` / `false` or `GUARDIAN_PKG_VET=0`, or an `enabledPlugins` entry turning dev-guardian off (`"dev-guardian@<marketplace>": false`), switches the hooks off. An assistant's `Write` / `Edit` / `MultiEdit` of those files is denied when its **result** sets one of those that the file did not already set; every other edit — permissions, other environment variables, other hooks, other plugins, and any edit of a file where the user already set such a key — goes through. A shell write of those files (a redirection, `mv tmp .claude/settings.json`, `jq … | sponge`, `sed -i`, program text naming the file) cannot be read reliably, so it is judged by the command's text: it is denied when the command names `disableAllHooks`, `GUARDIAN_HOOKS`, `GUARDIAN_HOOKS_BASH_BLOCK`, `GUARDIAN_PKG_VET`, or `enabledPlugins` together with `dev-guardian`; `jq '.permissions…' … > tmp && mv tmp .claude/settings.json` goes through. The shell rule matches the key's **name**, whatever the value, so it also denies writes that do not loosen anything: setting `GUARDIAN_HOOKS_BASH_BLOCK` to `1`, `"disableAllHooks": false`, deleting such a key (`jq 'del(.disableAllHooks)'`), or `"dev-guardian@…": true` in `enabledPlugins` — make those edits with `Write` / `Edit`, which judge the result. `claude plugin disable`, `uninstall` or `marketplace remove` naming dev-guardian is denied too.

**Known limits.** None of the following is refused. Each can change what the hooks do, and switching the guardrails off stays the user's decision — these are recorded so nobody reads the guards as covering them:

- a program written to disk and then run — `python fix.py`, `node tool.mjs`, `pwsh ./x.ps1`, a build script, an editor — can never be judged: what it does is not in the command, and the file it runs can be written by any earlier step;
- other programs that write files by their own means: `git checkout` / `restore` / `stash` of a tracked config file, an archive extracted into a configuration directory (`tar -x -C`, `unzip -d`, `Expand-Archive`), `find … -delete` / `-exec rm`, `awk -i inplace`, and a path handed over at run time — a variable (`echo … > "$F"`), `$(…)`, `xargs`, a PowerShell pipeline (`Get-ChildItem … | Remove-Item`), `Join-Path` outside program text, or program text that builds the path from pieces other than whole string literals (`'dev-' + 'guardian'`);
- a Claude Code settings file prepared elsewhere and then copied into place (`cp /tmp/s.json .claude/settings.json`): the command that writes it names no loosening key;
- removing the project's whole `.guardian` directory, or everything in it (`rm -rf .guardian`, `.guardian/*`) — it also holds the scan database, and the project configuration it deletes could only have made the guard stricter; likewise moving or removing a parent of `~/.config/dev-guardian` (`mv ~/.config …`), which leaves the protective defaults;
- the plugin's own installed files (`hooks/`, `mcp/dist/` under `~/.claude/plugins/…/dev-guardian`): editing the guard's code switches it off, and no hook can protect an installation from the account that owns it;
- nesting past the guard's depth: a script handed to `bash -c`, `sh -c`, `eval`, `pwsh -c`, `npx -c`, a `cmd /c` line or a script fed to a shell is fully judged three levels deep (a `cmd /c` line's file effects eight); anything nested deeper is not judged, and the command warns "part of this command was not assessed (nested more than 3 levels deep)" — never a silent `ok`, but `cmd /c cmd /c cmd /c cmd /c rd /s /q C:\` only warns;
- a command inside a double-quoted string — `echo "$(rm -rf /)"`, PowerShell's `"$(Remove-Item …)"` subexpression, or one in an expandable `@"…"@` here-string — is not judged;
- launchers other than those named above (`volta run`, `pipx run`, `corepack`, a shell alias or function) are not followed to the program they run;
- a statement longer than 16 KB: the pattern rules (force-push, `curl | sh`, `chmod -R 777 /`, …) read its first 16 KB only; a command longer than 512 KB is read to that length (the longest real command measured was 58 KB); and an assessment that runs past its 2.5 s budget stops, as does one that fails part-way on an input nobody foresaw. Each is a warning that names it — "part of this command was not assessed (over 16 KB)", "(over 512 KB)", "(assessment time budget exhausted)", "(the assessment failed)" — never a silent `ok` and never no answer at all (a block found before it still blocks), but what lies past it is not judged: `rm -rf /` after 512 KB of padding only warns. The per-command checks (`rm -rf`, the configuration files, program text) read the whole statement.

## The same detectors from a terminal

```text
node cli/dev-guardian.mjs check --file path/to/file      # secrets, exit 1 on a finding
node cli/dev-guardian.mjs check --bash "rm -rf /"         # ok / warn / block, exit 1 unless ok
node cli/dev-guardian.mjs check --bash 'Remove-Item "C:\Users\" -Recurse' --powershell   # as the PowerShell tool
node cli/dev-guardian.mjs check --file .env --min high --json
```

Exit code 2 is a usage error — neither or both of `--file` and `--bash`, an unknown argument, a `--min` other than `high` or `medium` — or an unreadable `--file`. A file is read as UTF-16 when it starts with a UTF-16 byte-order mark or its bytes are NUL-interleaved (what PowerShell 5.1's `>` and `Out-File` write), as UTF-8 otherwise.
