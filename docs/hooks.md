# Guardrail hooks

With the plugin enabled, Claude Code loads [`hooks/hooks.json`](../hooks/hooks.json) automatically. Every hook runs one dispatcher, [`hooks/guardian-hook.mjs`](../hooks/guardian-hook.mjs), which imports only Node built-ins and the pre-built detectors in one bundle, `mcp/dist/hooks.js`, and the part of it the event runs (`hooksBash.js`, `hooksWrite.js`, `hooksVet.js`, `hooksSession.js` beside it) — no `npm install`, no native module.

Three rules hold for all of them:

- **Fail open.** Any error inside a hook exits 0 with no output. A guardrail that breaks must not break your session. `GUARDIAN_HOOKS_DEBUG=1` prints what went wrong on stderr. It is not silent, though: when the shell guard, the secret scan, package vetting or the settings guard cannot be loaded (a missing or damaged `mcp/dist/hooks.js`, or one of its parts), SessionStart says which ones are off for the session — each one fails open alone: a damaged shell guard leaves package vetting running — and, when the plugin's `mcp/dist/engine.js` is missing or not the file the build wrote (its size and SHA-256 are checked, the file never loaded), that the MCP tools and the CLI cannot run; when its own checks (`hooksSession.js`) cannot be loaded, that the briefing has no branch line, no database registration check and no engine check.
- **Only what just happened.** A hook assesses the text just written or the command about to run — it never scans the repository. It does read a little around it: SessionStart runs one `git status --porcelain=v2 --branch --ignore-submodules=dirty` — none in a folder with no `.git` at it or above it, where git would find no repository — hardened like every git dev-guardian starts, so the project's own `core.fsmonitor`, hooks and filter drivers do not run, nor its submodules' (their uncommitted work is not counted; a moved submodule commit is); without `mcp/dist` to harden it, git is not run at all and the branch line is left out ([SECURITY.md](../SECURITY.md#hardening-posture)) — and checks `.guardian/`, and the install hook reads registry configuration (`.npmrc`, `pip.conf`, `package.json` workspaces, … — listed below). The authoritative scans stay in the MCP tools (`scan_secrets`, `vet_packages`, …).
- **One file is written.** SessionStart leaves a small mark in dev-guardian's per-user data directory — never in the project — so that `health_status` can tell a session in which no hook started at all: [the session mark](#the-session-mark). No other hook writes anything.

Each hook has a 15 s timeout in `hooks.json`. Every entry is in exec form — `"command": "node"` with the dispatcher and the event in `"args"`, no shell between Claude Code and node — which needs **Claude Code 2.1.139 or later**; a shell per call cost 50-130 ms on every Bash call. An older Claude Code does not pass `"args"`: no hook starts at all, and none can say so — not even SessionStart, which never runs. Nothing else in the plugin depends on the version.

The write guards run for Claude Code's own write tools and for a third-party MCP server's: a tool named `mcp__<server>__<tool>` whose name holds a file verb, in any case — `write`, `edit`, `create`, `move`, `rename`, `copy`, `append`, `patch`, `replace`, `save`, `put`, `upload`, `insert` (and, before the call, `delete`, `remove`, `unlink`) — or `update`, `modify`, `apply`, `set` or `push` as a word of the name (`update_file`, `apply_diff`, `set_file_contents`, `fileUpdate`, `push_files`; not `get_settings` or `reset_cache`) — such as `mcp__filesystem__write_file`, Serena's `create_text_file`, JetBrains' `replace_text_in_file` or `str_replace_editor`. The tool's name is what follows `mcp__<server>__`, `__` and all (`write__v2`). Every string argument is read, to four levels deep and 256 strings: the usual path names (`path`, `file_path`, `filePath`, `relative_path`, `pathInProject`, `destination`, `target`, `to`, a `file://` URI, `paths`, `files`, and any key that names a path, a file, a directory, a folder, a destination or a target — `target_file`, `outDir`; a move's or a rename's `source` as the path it takes away, a copy's as one it only reads) are paths it writes, and — for a tool whose name names a file (`file`, `path`, `dir`, `folder`, `notebook`, `document`: `write_file`, `push_files`) — so is any other short, single-line string (the first 32). For another tool, such a string that ends in `.json` or names `registry` (the first 32) is still compared with the guarded files, and one that names one — the hook configuration, the registry, Claude Code's settings (`save {location, data}`, `write {args: [path, content]}`) — is **asked about**, never denied: a GitHub `create_issue` titled `.claude/settings.json` is the user's to judge, and one titled anything else says nothing. A path that starts with `~` (`~/…`, `~\…`), which the filesystem server and desktop-commander expand, is judged both as written and as the home directory's, and so is — on Windows — an MSYS `/c/…` as `C:/…`; the same holds for `Write`, `Edit`, `MultiEdit` and `NotebookEdit`; its text is `content`, `text`, `data`, `file_text` or its edits (`oldText` / `newText`, `old_str` / `new_str`, `edits`), or else every string that is not a path. A call with an argument past those limits is not taken as read: after every guard passed what was read, a tool whose name names a file is **asked about** ("did not read all of …'s arguments"), and another one gets a note.

## What runs when

| Event | Matcher | What it does | Default |
| --- | --- | --- | --- |
| `SessionStart` | — | Briefs the agent: plugin version, branch, uncommitted changes, whether the project has a `.guardian/` directory and when the database last changed, whether that database is registered as the user's (read from the user's registry, never by opening the database) — and, when the project's hook config asked to loosen a guardrail, that it was ignored. A project with no `.guardian/` gets one line saying the user can run `/guardian-init` — only when the folder looks like code (version control, or a manifest: `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml`, a `.sln` or `.csproj`, …). It also leaves [the session mark](#the-session-mark). | on |
| `PostToolUse` | `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, MCP write tools | Scans the inserted text for hard-coded secrets (medium confidence and up) and adds a warning with a **redacted** preview. A long line — a one-line JSON file, a minified bundle — is read to its end, in 16 KB windows overlapping by 2 KB (8 KB for JWTs), so every match lies whole in one of them. | warn |
| `PreToolUse` | `Bash`, `PowerShell` | Assesses the command: **denies** catastrophic ones, **asks the user** about an agent-run `baseline update`, warns on risky ones, then vets any package it would install. | deny catastrophic |
| `PreToolUse` | `Write`, `Edit`, `MultiEdit`, MCP write tools | **Denies** any edit of the guard's own configuration, and an edit of Claude Code's `.claude/settings*.json` that would switch the hooks off (below). | always — unless every hook is switched off at user level |
| `PreToolUse` | `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, MCP write tools | **Denies** any write into dev-guardian's registry of trusted databases (below). | always — unless every hook is switched off at user level |
| `PreToolUse` | `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, MCP write tools | Denies writing a high-confidence provider token (AWS, GitHub, Stripe, Hugging Face, …) — not a documented placeholder such as AWS's `…EXAMPLE` keys or `sk-your-…-here`. | off — opt in with `"secrets": { "block": true }` |

## The session mark

SessionStart writes one small file, and it is the only thing any hook writes: `<data dir>/hooks-heartbeat/p<key>.h<pid>.json`, in dev-guardian's per-user data directory ([below](#the-database-registry): `GUARDIAN_DATA_DIR`, or the per-OS default) — never in the project. It holds the date, the plugin's version, how the session began (`startup`, `resume`, `clear`, `compact`, `fork`), the id of the Claude Code process that started the hook and a 16-character key derived from the project's path. No path, no file name or content, no command, nothing of the environment.

It is there because a hook that never starts cannot say so. A Claude Code older than 2.1.139 starts no hook at all (above), while the MCP server goes on answering as if the session were guarded. `health_status` looks for the mark of the Claude Code process that started the server and returns `hooks.state`:

| `hooks.state` | When | `hooks_warning` |
| --- | --- | --- |
| `running` | a hook of this session's Claude Code process left its mark (`matched_by: "host_process"`), or — where that process cannot be matched — one of this project did since 120 s before the server started (`matched_by: "time"`) | — |
| `pending` | no mark, and the server started less than 30 s ago | — |
| `not_observed` | no mark, past those 30 s | says so: commands, writes and installs are not being assessed, and what to check — the Claude Code version (it is named when the server sees one older than 2.1.139), the `node` the hooks find, Claude Code's own hook settings |
| `disabled_by_user` | the hooks are switched off by the user's own setting, which it names | — |
| `not_applicable` | the server was not started as the plugin's own — another host, or a server configured by hand, where no hook of the plugin runs | — |
| `unknown` | no mark, and the data directory could not have held one (not writable, not a directory, on the network) | — |

- **It cannot hold the session.** The mark is started first, beside git and the session's checks, and awaited for a second at most. Nothing is asked of the filesystem about a data directory on the network, a temporary file is created exclusively and renamed over whatever has the mark's name — a link or a FIFO there is replaced, never opened — and a write that fails changes nothing the session sees: `GUARDIAN_HOOKS_DEBUG=1` says why.
- **Switched off, it is still written.** With `GUARDIAN_HOOKS=off`, or `"enabled": false` in the user-level file, SessionStart does nothing else but still leaves the mark, saying `disabled`: it is how `health_status` tells "switched off by the user" from "never started". No other event writes anything, switched off or not.
- **It only informs.** Nothing decides a guard, the trust in a database or a scan's result by it, and only `health_status` reads it. A mark that cannot be read, is not valid, is dated in the future or is not named for its own content counts as absent. So does every mark in a data directory inside the project, whatever it says — a repository could ship one for every plausible process id — and the warning then says so.
- **It is cleaned up.** Each SessionStart removes the marks older than 30 days and those of a Claude Code process that no longer exists, 64 at most, and nothing else. Deleting the `hooks-heartbeat` directory removes them all; the next session recreates it.
- **Both sides must look in the same place.** A `GUARDIAN_DATA_DIR` set for the server and not for the shell that launches Claude Code (or the reverse) leaves the server with no mark to find, and it reports `not_observed`.

The mark says that the host started the hooks. Whether the detectors behind them answer — a catastrophic command denied, a write that switches the hooks off refused, a secret warned about, the install of a package npm took down denied — is the other half, and `dev-guardian selftest` checks it by handing the installed dispatcher each of those as text: see [selftest.md](selftest.md).

## The shell guard

The same detector serves `Bash` and `PowerShell` and the CLI's `check --bash`. It splits a command line into statements and also reads text that is fed to a shell (`bash <<EOF … EOF`, `echo '…' | sh`); a heredoc handed to a non-shell command (`git commit -F - <<EOF`) stays inert.

From the **PowerShell tool** the command is read twice — as a POSIX shell quotes it, and as PowerShell does (a backslash is literal, a backtick escapes, `''` inside `'…'` and `""` inside `"…"` are one quote, typographic quotes are quotes, a here-string `@'…'@` is one literal, `<# … #>` is a comment, after `--%` the rest of the line — up to a `|` — goes to the program unparsed, the commands in a script block, `ForEach-Object { … }` included, are assessed like any other, a braced variable is one word to its `}` whatever its name holds (`${"}`, `${env:ProgramFiles(x86)}`), and a double-quoted string or an `@"…"@` here-string lasts as PowerShell's own tokenizer reads it — a `$( … )` in it to the `)` its parentheses alone balance, a braced variable `${…}` to its `}`, so a quote inside either does not end it — while the subexpressions it runs are assessed as PowerShell scripts of their own) — and the more severe verdict stands. Read the POSIX way alone, an ordinary Windows path ending in `\"` escapes its closing quote and swallows the rest of the line: `Remove-Item "C:\Users\" -Recurse -Force` was `ok`. Program text handed to `pwsh -Command` / `-EncodedCommand` is read both ways too, from either tool. Both readings treat a `#` that starts a word as a comment to the end of the line — not one that continues a word, as after `$(…)` in bash or `=` in a PowerShell argument. `check --bash "…" --powershell` reads a command the same way.

It is a speed bump, not a wall: the other ways to launch it are in the known limits below, and what the command writes is guarded by path ([the database registry](#the-database-registry)).
- **Asked — the user decides**: `baseline update` run by the assistant, in the same spellings (`dev-guardian`, `node …/cli/dev-guardian.mjs`, `node .specs/guardian.cjs`, behind a runner, in a nested script or launched by `Start-Process` / `find -exec`). It accepts every current finding into `.guardian/baseline.json`, a feature's own new one included, and the gate stops reporting them; Claude Code shows the user why and asks. To accept one reviewed finding, suppress it inline with a reason (`nosemgrep: <rule> -- <reason>`, `# nosec`), or rebuild the baseline on the base commit. Asked too: a command that deletes Claude Code's settings or moves them away — `rm .claude/settings.json`, `mv .claude/settings.local.json x`, `Remove-Item .claude\settings.json`, `del`, `unlink`, `Move-Item`, `Rename-Item`, `[IO.File]::Delete`, the files matched as their writes are (below; `CLAUDE_CONFIG_DIR` and the managed settings included); through a glob that could match one (`rm .claude/settings*.json`, `rm .claude/*`, `Remove-Item .claude\settings*` — judged by what it can match, never expanded on disk, a directory's name only by a pattern that begins as the name does, so `rm -rf build/*` names no `.claude`); with the whole directory that holds them (`rm -rf .claude`, `rm -r ~/.claude`, `Remove-Item .claude -Recurse`, `rd /s /q .claude`, `mv .claude x`, `"$CLAUDE_CONFIG_DIR"` itself, a glob such as `.clau*`); by `git rm` or `git mv` of them (not `git rm --cached`, which only untracks, nor `-n`; git's own `*` crosses `/`, so `git rm '*.json'` counts); and by `find` with `-delete` or an `-exec` / `-ok` of `rm` or `mv` (also `| xargs rm`) — from a start path that names them, unless its `-name` / `-path` tests rule them out (`find .claude -name '*.md' -delete` is not asked about), or from one above them (the working directory, the home directory, the project) whose tests can match them within any `-maxdepth` (`find . -name settings.local.json -delete`) — which takes every `permissions.deny` rule they hold with it; a copy of them is only a read, and one provably elsewhere (another project's, a fixture's) only warns. And a command the guard could not read to its end — over 512 KB, a statement over 16 KB, past the 2.5 s assessment budget or nested more than three levels deep — since padding a command that would be denied past one of those limits would otherwise run it with only a note; the question names the limit. With the block switched off each is only a warning.
- **Warned**: force-push, `git reset --hard`, `git clean -fd`, `chmod 777`, clearing shell history, `sudo`, any other recursive delete, `find ~ … -delete` with a test that narrows it (`-name`, `-mtime`, …), `find . -delete` with none, `chmod -R` / `chown -R` of a system directory, a decoded script, or any other script a shell, `iex` or cmd.exe reads, that cannot be read (above), `vssadmin delete shadows`, `reg delete HKLM\…`, `terraform destroy`, `aws s3 rm --recursive` / `aws s3 rb --force`, `gh repo delete`, and — in a hook call, which knows the project and the working directory — a write of a file named like the hook configuration or Claude Code's settings that lies outside them and the home directory (another project's `.guardian/hooks.config.json`, a test fixture's fake HOME), which is not the one this session reads.

The deny message never says how to switch the guard off. That takes the user-level config or `GUARDIAN_HOOKS_BASH_BLOCK=0`, and an assistant's `Write` / `Edit` of either config file — or a shell write onto it that the guard can see — is itself denied.

## Install-time package vetting

When the command installs packages by name — `npm i|install|add`, `pnpm add|i|install`, `yarn add`, `bun add|i|install`, `pip install`, `uv add`, `uv pip install`, `poetry add`, `composer require`, `dotnet add package`, `dotnet package add` (.NET 10), `dotnet tool install` — or downloads one to run it — `npx`, `npm exec`, `pnpm dlx` / `pnpx`, `yarn dlx`, `bunx` / `bun x`, `uvx` / `uv tool run`, `uv tool install`, `pipx install`, `pipx run` (the package is the first word after the launcher's own options, or the value of its `-p` / `--package` / `--from` / `--spec`, plus `uvx --with`; the words after it are the program's, unless the program is a package manager — see "A launcher that runs a package manager" below; `npx`, `npm exec` and `bunx` of a bin the project has installed fetch nothing and are not vetted — judged as npm resolves it: a `node_modules/<name>/package.json` whose `name` is the package, in npm's prefix (the nearest directory, from where the command runs up, with a `package.json` or a `node_modules`), or for an unscoped program name not given by `-p` a `node_modules/.bin/<name>` that is a file, in the prefix or above it up to the repository root. Where the command runs is the working directory moved by the `cd`s that surely ran — at the head of a list or joined to it by `&&`, outside a pipeline, the background, a compound command (`if`, a loop, `{ … }`) and a function body, not a bare name under `CDPATH`, and into a directory that is there through no symbolic link or junction — npx runs in the link's target, where the walk up for an installed bin would answer for another directory than the path as typed (the shell guard's tracker of the line, `shell/workdir.ts`); `--prefix` / `-C`, `env -C` and `sudo -D` move it where this does not look, so nothing is taken as installed) — the hook runs the same checks as the `vet_packages` tool, under one **3 s** network budget for the whole command line and one **8 s** deadline for everything the hook call does (`GUARDIAN_PKG_VET_DEADLINE_MS`, at least 3000 — the network budget — and at most 12000, counted from the start of the call) — Claude Code kills a hook at 15 s, and the command then runs with no verdict at all. The process ends 250 ms after its answer is written, even when an unresponsive network still holds a connection open (it used to linger 5 s more, and Claude Code waits for it). A command that names no installer at all does not load the vetting code. The scripts a command hands a shell — `bash -c '…'`, `eval`, a `cmd /c` line, `pwsh -c` / `-EncodedCommand`, a script fed to a shell (`echo '…' | sh`, `cat <<EOF | bash`, base64 decoded into one), as the shell guard reads them — are vetted the same way, each read as its shell reads it; an install found there is never denied as missing (it is not one plain install statement), and a launcher there is not taken as running an installed copy once the outer command changed directory. Local work — reading registry configuration, walking a workspace — happens after the network and only for a name the registry does not have, each file read and each workspace walked once per call; what the deadline leaves unchecked reads "vetting time budget exhausted" and is never reported as vetted. It looks each package up once, at most 50 packages per command — names not on the popular list first, so padding a command with popular names cannot push another past the cap (a note says how many more were not vetted) — and reads a command for installs to 512 KB (past that, no missing-name deny, and a note says so, even when the first 512 KB install nothing):

| Finding | Hook answer |
| --- | --- |
| A version that would install is **malicious** (OSV `MAL-` advisory, or npm's `0.0.x-security` placeholder) | **deny**, in every command shape; the message says to ask the user to install it themselves |
| The name does **not exist** on the public registry | **deny** only when the whole command, comments stripped, is ONE plain install statement — a bare tool name (no `.venv/bin/pip`, `sudo`, `env`, `VAR=x`), no `&&`, `\|\|`, `;`, pipes, `&`, subshells, `$(…)`, backticks, variables, redirections, unquoted commas or `'…''…'`, and only flags from a small per-tool allowlist that cannot change where a package resolves from (not `composer --no-update` / `--no-install` or `dotnet --no-restore`, which defer the lookup) — and nothing below explains the 404. Otherwise a warning: "not found on the public registry — if it is private or local, ignore this". |
| Published less than 72 h ago, npm install scripts, typosquat suspicion, an unpublished exact version | warning |
| Known vulnerabilities | warning, only for an exact version pin (for a range the installed version is unknown) |
| A check could not run (offline, timeout, HTTP error, rate limit, `GUARDIAN_OFFLINE=1`) | one line saying the package was **not** verified — also when the same package has a warning; the command runs |
| Every package clean | silent |
| A command that installs nothing | silent, and no network request at all |

A missing-name deny carries its own escape hatch, named for the tool: re-run the install with an explicit `--registry <url>` (npm, `npx`, pnpm, bun), `--index-url <url>` (pip, `uv pip`, pipx), `--index <url>` (`uv add`, `uvx`, `uv tool`) or `--source` (poetry, dotnet), or prefix the command with `GUARDIAN_PKG_VET=0` — from the PowerShell tool, `$env:GUARDIAN_PKG_VET = '0'` first in the same command. Composer and Yarn Berry have no registry flag, so theirs names only the prefix. Either way the command is no longer one plain install statement; the hook's own switch is untouched, and a malicious version is still denied. A malicious-package deny has no escape hatch.

**Through `corepack`, and `yarnpkg`.** An install through `corepack <manager>[@version]` — the manager one of `yarn`, `yarnpkg`, `pnpm`, `pnpx`, `npm` and `npx`, in lower case, as corepack reads it — is read and decided as the manager's own line without `corepack`, and `yarnpkg` is read as `yarn`. `corepack use <manager>` and `corepack up` are read as a manifest install (below). The manager that corepack itself downloads is not vetted, and neither is an install behind another tool runner (`volta run`, `mise exec --`, …): both are in the [known limits](hooks-known-limits.md).

**A launcher that runs a package manager.** `npx pnpm add <p>` downloads `pnpm` and `pnpm` then installs `<p>` and the project's `package.json` (measured 2026-11-20 in a Linux container with npm 11.19, pnpm 11.24, Yarn 1.22 and 4.18, bun 1.4 and corepack 0.36, against a substitute registry that logged every request: the registry was asked for the manager, then for `<p>` and for the manifest's dependency, and both were installed). So when the word a launcher of the npm family (`npx`, `npm exec` / `npm x`, `pnpm dlx` / `pnpx`, `yarn dlx`, `bunx` / `bun x`) runs is `npm`, `pnpm`, `yarn`, `yarnpkg`, `bun` or `corepack`, with or without a version, the words after it are read as a command of that manager and vetted as the line without the launcher would be, beside the launched manager, which is vetted as before: `npx pnpm add <p>` vets `pnpm` and `<p>`, `npx corepack yarn add <p>` reads `corepack yarn add <p>`, `npx corepack up` and `npx corepack use pnpm@11` read a manifest install. A `--` next to the launched word is dropped. The manifest of the project is read for it (its dependencies' names go to the registry and to OSV): `npx yarn` and `npx pnpm install` read it too; with a directory or workspace flag on the launcher (`--prefix`, `-C`, `--dir`, `--cwd`, `-w`, `--workspace`, `--workspaces`, `--filter`, `-F`) one line says the `package.json` was not read. A name the registry does not have is DENIED only in the forms that were measured — `npx pnpm add <p>`, `npx yarn add <p>` and `npx corepack yarn add <p>` (also with `-y`), `npm exec -- pnpm add <p>` and `npm exec corepack -- yarn add <p>`, `pnpm dlx yarn add <p>`, `yarn dlx pnpm add <p>` (started by `corepack <manager>[@version]` or not) and `bunx pnpm add <p>` — in a plain single statement, with any version of the launched manager and only the flags of the inner manager's confident list (`-D`, `-E`, …). Any other form is vetted and only warns for a missing name: another pair (`bunx yarn add <p>`, `npx npm install <p>`), another spelling (`npm x`, `bun x`, `pnpx`), another flag of the launcher (`--yes`, `--no-install`, `-p`), a `--` in another place, another verb (`npx pnpm install <p>`), another manager or a version behind `corepack`; a package OSV lists as malicious is denied in all of them. The inner command is read one level deep: behind `npx npx pnpm add <p>` only the first `npx` is vetted, and behind `npx pnpm dlx yarn add <p>` `pnpm` and `yarn` are, not `<p>`. When the words after the manager are no command the hook reads (`npx pnpm --version`, `npx yarn run build`, `npx corepack enable`, `npx pnpm exec <tool>`) only the launched manager is vetted. The [known limits](hooks-known-limits.md) list what stays.

### A manifest install

A command that installs from a manifest names no package — the manifest does; and a command that names a package inside a project installs the project's `package.json` as well, so the manifest is vetted for it too (below). `npm install` with no package, `npm ci`, `npm install-ci-test`, `pnpm install`, `yarn`, `yarn install` and `bun install` — and the maintenance verbs `npm dedupe`, `npm prune`, `npm audit fix`, `pnpm dedupe`, `yarn dedupe` and `yarn up` with no pattern, which install it as `install` does — install the nearest `package.json` from the directory they run in upward, as the managers find theirs (a folder with none installs the one above it); the hook reads that one, up to the project root (the root of the git repository when the session was opened in a subfolder of one) and no further — the lockfile is looked for from the directory of the file found, and a file above that root is not read (a [known limit](hooks-known-limits.md)). `pip install -r` (also `uv pip install -r`) installs the requirements files it is given. The hook reads that manifest — the `dependencies`, `devDependencies`, `optionalDependencies` and `peerDependencies` of the `package.json`; the packages each requirements file names, and those of the files it includes with `-r`, three levels deep and eight files in all — and looks its packages up with the ones the command names, under the same budget and a cap of their own: 150 packages of manifests, names not on the popular list first, beside the 50 a command line may name (a note says how many more were not vetted). Real applications declare more direct dependencies than anyone types: of 16 manifests measured, 11 had from 57 to 97. An npm alias (`"x": "npm:real@^1"`) is looked up as the package it installs. For Yarn and bun `npm:` is also the registry protocol, so a `"x": "npm:^1"` is the package `x`, and a `"x": "npm:1.0.0"` or `"x": "npm:latest"` looks up both `x` and the word after `npm:` (the same reading as `yarn add x@npm:1.0.0`, below). Only a valid registry name with a valid range is taken from a manifest. `npm install-test` and `npm it` are read as `npm install` in everything: with no package they install the manifest, and `npm install-test <package>` is read as `npm install <package>` (measured with npm 11.19: the package is installed beside the manifest, and with `-g` alone). An install that names a package (`npm install|i|add <package>`, `pnpm add|install <package>`, `yarn add`, `yarn workspace <w> add`, `yarn workspaces foreach … add`, `bun add|install <package>`) installs the project's `package.json` beside it, so the hook reads that manifest too, with the manifest's rules (the table below: only a malicious package denies) and the named packages' by-name rules (a name the registry does not have is denied in a confident shape); the named packages are looked up first, so a manifest that is slow to answer never leaves one unvetted, and the line that says how many packages of the manifest could not be vetted is said as for a bare install. A word that is skipped (a path, an archive, a URL: `npm i ./pkg.tgz`) does not stop the manifest from being read. It is not read for an install that is global for certain, nor for a launcher of another package (`npx cowsay`, `pnpm dlx create-thing`), which does not install it — a launcher that runs a package manager does, and its manifest is read ("A launcher that runs a package manager", above); where the command runs is not known (`--prefix`, `-C`, `--dir`, `--cwd`, a `cd` that may not have run), the named packages are vetted and one line says the `package.json` was not read (measured with npm, pnpm, Yarn 1 and 4, and bun). A bare `npm install` or `pnpm install` is read as a manifest install unless it is global for certain (see the global install rule below), and for npm and pnpm a `true` or `false` right after a boolean flag is the flag's value, not a package: `npm install -D false` and `npm install --force true` install the manifest, and so does `npm -D false install`. The loglevel flags `--silent`, `--quiet`, `-q`, `--verbose` and `-d` take no such word: the word after them is a package. After a short cluster the word belongs to its last letter (`-qD false` is a manifest install, `-Dq false` names the package `false`), and a cluster that holds a `g` is never read as global. A flag written with `=` takes nothing after it (measured with npm 11.20 and pnpm 10.33). In doubt the manifest is read. The answers are fewer than for a package named on the command line, because a manifest is installed again and again:

| Finding, for a package the manifest names | Hook answer |
| --- | --- |
| **Malicious** (OSV `MAL-` on the version its range resolves to, or on a version the lockfile pins, or npm's security placeholder) | **deny**, naming the file and the package; the message says that installing it or removing the dependency is the user's decision, and names no way round |
| Typosquat suspicion; a name the public registry does not have | warning, naming the file — a missing name never denies a manifest install, where it is usually a private or a workspace package. One answer lists the first five missing names, of all the manifests it read together; one line counts the others and names their files (`dev-guardian: 145 more packages of package.json are not on the public registry either (…) — not listed.`). They are all looked up as before. A missing name close to a popular package's (`Did you mean '…'?`) and a typosquat suspicion are always listed |
| Published less than 72 h ago, npm install scripts, known vulnerabilities | not reported: each would be repeated at every install (`deps_audit` reads the manifest and the lockfile). The first two are not looked up either: for a package of a manifest the hook asks the registry for one document — npm's abbreviated one — and OSV for the batch, never npm's full document or a version's own, which only those two checks need |
| A check could not run | one line: how many packages of which file were **not** verified |
| The manifest is there and was not read (not a regular file, over 1 MiB, not valid JSON, on a network path), a file it includes was not, or where the command runs is not known (`--prefix`, `-C`, `--dir`, `--cwd`, a `cd` that may not have run) | one line: what was not read, and that its packages were not vetted |
| The manifest is not there; every package clean | silent |

**The lockfile.** For an npm-family manifest install the hook also reads the manager's own lockfile — `package-lock.json` or `npm-shrinkwrap.json` (v1 to v3), `pnpm-lock.yaml` (5, 6 and 9), `yarn.lock` (v1 and Yarn 2+) or `bun.lock` — in the directory the command runs in or the nearest one above it, up to the project root. With a lockfile, the pinned name and version of every dependency, the transitive ones too, go to OSV for malicious-package advisories: up to 8 000 pairs a call, in batches of 500. The registry is then asked only for the direct dependencies the lockfile does not cover; it covers one when it records, for that project, the same range the manifest has, with a pinned version that satisfies it. A `MAL-` advisory denies, and so does the pair a registry-shaped `resolved` URL really fetches when it differs from the entry. Everything else is said, never denied and never silent: a lockfile that was not read, entries that were not recognised, pairs with no complete answer from OSV, pairs past the cap, packages fetched from another source (asked like the rest, and silent only for a URL of a registry the user's own npm configuration names), and a scope that a project file gives a registry of its own (not sent). A package fetched from another source is said by the host of its URL, unless the URL, as written in the lockfile, has an `@` outside its credentials (a credential written with a `/`, `?`, `#` or a backslash in it: the URL parser then reads the start of the credential as the host): the line then says `comes from another source` with no host, and the entry is still counted. The `@` that opens the scope of the entry's own package (`/@scope/name/-/…`) is not such a sign. Without a lockfile the manifest's direct dependencies are vetted as above. An update verb (`npm update`, `upgrade`, `up`; `pnpm update`, `up`, `upgrade`; `yarn upgrade`, `yarn up <pattern>`; `bun update`) installs the manifest's dependencies past what the lockfile pins, so every direct dependency is vetted by name at the registry even when the lockfile covers it (the pins still go to OSV), and the names given to a project update (`npm update lodash`, `pnpm update <name>`, `bun update <name>`, `yarn upgrade <name>`) select dependencies of the manifest: they are not looked up as new packages. Where the update fetches the name itself it is vetted as a package named to an update (measured on 2026-11-20 with npm 11.19, pnpm 11.24, Yarn 1.22, 3.8 and 4.18, and bun 1.4): the names given to a global update (`npm update -g <name>`, `npm up` and `npm upgrade`, `pnpm update -g`, `bun update -g`, `yarn global upgrade <name>`) and to the `up` forms of Yarn (`yarn up <name>`, `yarn workspace <w> up <name>`, `yarn workspaces foreach … up <name>`) are looked up when no manifest read for the command has them, or when they carry a version or a range. A malicious one denies and a typosquat suspicion warns; a name the registry does not have only warns — an update fetches a package only when it is installed already, which the hook cannot see — and a recent version, install scripts and vulnerabilities are not said. A global update with no name says in one line that it updates every globally installed package and that none was vetted. The by-name check follows the manifest's range and cannot know which version the manager will pick: with `--latest`, `yarn up <name>` or `bun update --latest` it may install a version outside that range, which was not vetted. A global update for certain (`npm update -g`) reads no manifest.

**What leaves the machine.** With a lockfile, the names and pinned versions of all its registry packages — transitive ones included — are sent to OSV at every manifest install — and at every install that names a package inside a project, which installs the manifest too — and the registry gets the names of the direct dependencies it does not cover, with their ranges; before, only the direct dependencies' names went, to the registry and to OSV. Without one, the names of the manifest's direct dependencies, with their ranges, are sent to the public registry and to OSV — as the names on a command line are, and for an install that names a package as for a bare one, nothing more — and nothing else of the file. A package of a scope that the npm configuration gives a registry of its own is not sent: in silence when the user's configuration names that registry, with one line when a file of the project does. `GUARDIAN_PKG_VET=0` switches the vetting off, the manifest's and the lockfile's with it. Workspace members and the other package managers' manifests are not read, and what the lockfile vetting leaves out is in [the known limits](hooks-known-limits.md#install-time-package-vetting).

From the **PowerShell tool** the command is also read the way PowerShell reads it: `npm i a,b` hands npm two packages, a backtick at the end of a line continues it, a backslash before a closing `"` is literal, `''` inside `'…'` is one quote, and a no-break space separates words. A package only that reading finds can be denied as malicious, never as missing.

**A project file that sets the default registry.** An install resolves from the registry the package manager is configured with, and the checks above ask the public one. When a file of the project sets the default registry (`registry=` in an `.npmrc`, `registry` in a `.yarnrc`, `npmRegistryServer` in a `.yarnrc.yml`, `[install] registry` in a `bunfig.toml`) to anything but the public registry, the hook adds one line to its answer for every install it vets, by name, from a manifest or through a launcher: `dev-guardian: the project's .npmrc sets the default registry (https://npm.company.example) — packages are fetched from it, and what it serves was not vetted.` It names the file by its base name only and the registry by `scheme://host` only — never the file's directory, nor the registry's credentials, port, path or query; a value with no readable host gives the line without the parenthesis, and so does one with an `@` outside its credentials, a comment cut off at a `#` or a `;` included (`registry=https://TOKEN#rest@host.example/`). That holds for the `.npmrc`, the `.yarnrc`, the `.yarnrc.yml` and an unquoted value in `bunfig.toml`: the value left after a comment is cut off still decides whether the registry is the public one, and an `@` in the comment only leaves the host unsaid, so `registry=https://registry.npmjs.org/ # owner: a@b.example` is the public registry and says nothing. The line is said once per call for a file, however many packages the command names. It changes no verdict: a malicious package is still denied, a missing name still warns with the configured registry as the reason, and the line stays out of a deny, like the other lines. These are the files each manager obeys, measured on 2026-11-18:

- npm 11.19 and 11.20 and pnpm 10.33 obey the project's `.npmrc` (not the `registry:` of `pnpm-workspace.yaml`).
- bun 1.4 obeys the project's `.npmrc` and `bunfig.toml`.
- Yarn 1.22 obeys the project's `.npmrc` and `.yarnrc`, and Yarn 4.18 its `.yarnrc.yml`: the word `yarn` does not tell the two apart, so for Yarn the hook counts the `.npmrc`, the `.yarnrc` and the `.yarnrc.yml`.

The default registry is read from these files beside the nearest `package.json` from where the command runs (the directory itself when there is none), and at a workspace root above it (a `package.json` with `workspaces`; for pnpm also a directory with a `pnpm-workspace.yaml`). Yarn also reads a plain directory above, up to the repository root. The managers do not agree on which of these files wins (a member's or the workspace root's, `bunfig.toml` or `.npmrc` in one directory), so the hook does not choose: every one of them whose default registry is not the public one gets its own line, the nearest first, at most three, and a last line counts the files left out. A line may therefore name a file the manager ends up not obeying. A file that sets the public registry hides no other, a key repeated in a file is read at its last line, as the managers do, and the home directory and what is above it are never read for this line. A global install (`-g`, `--global`, `--location=global`, `yarn global add`) gets no line: the manager does not obey the project's file there. It is read as global only when the command says so and no word can take it back: with `--global=false`, `-g false`, `--no-global`, `--location=project`, a word with a shell variable in it, or a global word standing where another flag's value goes (`--otp --global`), the hook does not take the install as global (npm, pnpm and bun read `-g` and `--global`; Yarn is global only through `yarn global add`, its `-g` takes a value). A flag the hook does not know beside it also makes the install not global, because npm reads abbreviations such as `--loc=project` that the hook's table does not hold. In doubt the line is said. The line is not said when the registry is one the user's own configuration names (the user npmrc or npm's global one, a registry variable, `~/.yarnrc.yml`, `~/.bunfig.toml`): a file of the project never silences it. It is not said either when the command line names a registry (`--registry`), when the environment sets one (`NPM_CONFIG_REGISTRY`, `YARN_NPM_REGISTRY_SERVER`, `YARN_REGISTRY` or `BUN_CONFIG_REGISTRY`), or when the directory the command runs in is not known (`--prefix`, `-C`, `--cwd`, a `cd` that may not have run). What stays is in [the known limits](hooks-known-limits.md#install-time-package-vetting).

What counts as "something explains the 404" — the hook reads files and environment only, never the network, for this:

- **npm, pnpm, yarn, bun**: `registry=` or `@scope:registry=` in the project `.npmrc`, the user npmrc (`NPM_CONFIG_USERCONFIG` or `~/.npmrc`), npm's global npmrc (`npm_config_globalconfig`, `npm_config_prefix`, `%APPDATA%\npm\etc\npmrc` or `<node prefix>/etc/npmrc`) and pnpm's global rc; yarn's `.yarnrc.yml` `npmRegistryServer` / `npmScopes` — in every directory from the project up to the filesystem root, as Yarn Berry reads it — and classic `.yarnrc`; bun's `bunfig.toml` (project or `~/.bunfig.toml`); an npmjs auth token when the name is scoped (a private scoped package answers 404 anonymously); a workspace package (`package.json` `workspaces`, `pnpm-workspace.yaml`) — a workspace is read to 3000 directories, and one larger than that, or cut short by the deadline, leaves a name it did not reach unknown, never absent.
- **pip, uv, poetry**: `pip.conf` / `pip.ini` (user, the environment's prefix — `VIRTUAL_ENV` or `CONDA_PREFIX` — `PIP_CONFIG_FILE`, `/etc/pip.conf`, `/etc/xdg/pip/pip.conf`, `XDG_CONFIG_DIRS`, `%ProgramData%\pip\pip.ini`, macOS `~/Library/Application Support/pip` and `/Library/Application Support/pip`); `uv.toml` (`UV_CONFIG_FILE`, `~/.config/uv`, `%APPDATA%\uv`, `/etc/uv`, the project); `[[tool.uv.index]]`, `[[tool.poetry.source]]`, `[[tool.pdm.source]]` or a `[tool.uv]` index in `pyproject.toml`; uv workspace members and `[tool.uv.sources]`.
- **Composer**: a `repositories` entry in `composer.json` or the user's global `config.json`.
- **NuGet**: any `nuget.config` from the project up to the filesystem root, the user-level one, every `*.config` in the extra user directories (`%APPDATA%\NuGet\config`, `~/.nuget/config`, `~/.config/NuGet/config`) and the machine-wide ones (`%ProgramFiles(x86)%\NuGet\Config`, `/etc/opt/NuGet/Config`, macOS `/Library/Application Support/NuGet/Config`), with a source that is not nuget.org — except that a machine-wide config's local-folder source (Visual Studio's `Microsoft.VisualStudio.Offline.config` is one on every VS machine) counts only for a package that folder holds (`<id>/` or `<id>.<version>.nupkg`, the id ending where a NuGet version begins — `Foo.2FA.1.0.0.nupkg` holds `Foo.2FA`, not `Foo`; a file name that splits more than one way counts for each id, so `foo.2.1.0.0.nupkg` holds `foo`, `foo.2` and `foo.2.1`).
- **The hook's environment**, case-insensitively: `npm_config_*registry*`, `YARN_NPM_REGISTRY_SERVER`, `YARN_REGISTRY`, `BUN_CONFIG_REGISTRY`, `PIP_*INDEX*`, `UV_*INDEX*`, and for NuGet only a variable that names a source, feed or configuration file (`NUGET_*SOURCE*`, `NUGET_*FEED*`, `NUGET_*CONFIG*`, `NUGET_FALLBACK_PACKAGES`) or a source's credentials (`NuGetPackageSourceCredentials_<name>`) — not `NUGET_PACKAGES` or `NUGET_XMLDOC_MODE`.
- **The command line**: any non-public `--registry`, `-i`, `--index-url`, `--source`.

These files are read like the hook configuration (below): a file reached through a link to a network or device path is not opened. A configuration that is there but could not be read — that link, a loop, a directory or FIFO where the file belongs, a file over 1 MiB, no permission — is **unknown**, never absent: it may name a private registry, so a missing name warns — "registry configuration at … could not be read — possibly a private registry", or, for a workspace's `package.json` / `pyproject.toml` or a directory that could not be listed, a message naming that — instead of being denied. A malicious version is still denied.

A registry that *is* the public one (`registry.npmjs.org`, `pypi.org/simple`, `api.nuget.org`) is not custom. A registry URL with credentials — or with anything but the public host (and the scheme's own port) in its authority, such as `https://registry.npmjs.org:x@evil.example/`, whose host is `evil.example` — counts as another registry. Paths, URLs, git specs (`git@host:repo` included), `file:` / `workspace:` specs, requirement files and flag values are never looked up, and neither is a word that the package manager of the command reads as an archive file (below); a bare `npm install` names no package, so what it installs is its manifest ([A manifest install](#a-manifest-install)).

A word after a flag the hook does not know is vetted as a possible package. The managers have more flags than the hook's tables hold, and a long flag it does not know (no `=`, not `--no-…`) may or may not take the next word as its value, so `npm install --prefer-dedupe <package>`, `yarn add --ignore-engines <package>` and `npx --ignore-scripts <package>` look that word up and the command is marked uncertain: a name the registry does not have is a warning ("not denied: unknown flag …"), never a deny, and a malicious one is denied as always. When that word is the only thing the command names, the manifest is read as for a bare install, because the word may be the flag's value. Before the subcommand the same rule applies the other way round, word by word and in one pass: the word after a flag the hook does not know is the subcommand only when it is one the hook reads, and any other is that flag's value, so `npm --some-flag 3 --engine-strict install <package>` and `yarn --some-flag 1` are read as the install they are. A `true` or `false` after an unknown flag is its value, for every manager, and is not looked up. A Yarn script behind such a flag (`yarn --some-flag build`) is read as a bare `yarn` too, so the manifest is vetted. Under the ceiling of 50 packages a command line is vetted for, the packages it surely names are taken before the candidate words, which fill what is left in line order (a command contributes at most 50 distinct candidates); the rest are counted in the "more packages in this command were not vetted" line. Many statements are answered within the hook's budget: a launcher's lookup of a copy in the project is made once per directory and name, and past the deadline it is no longer made, which the answer says.

**A `true` or `false` after a flag of a launcher.** Each launcher is read as its own manager reads it (measured 2026-11-19 with npm 11.20, pnpm 10.33, Yarn 4.18 and bun 1.4). `npm exec` and `npm x` follow the rule of `npm install`: a `true` / `false` after an exact boolean flag of npm (`--yes`, `--prefer-offline`, `--ignore-scripts`, `--no`, `-p`, …), or after a group of letters whose last one is such a flag (`-qy`), is the value of that flag, not a package, and the package is the next word; after a loglevel flag (`--silent`, `--quiet`, `-q`, `--verbose`, `-d`, `-s`), after a flag written with `=` and after `--` the word is the package, as npm fetches it. `-p` is a boolean flag there (for `npx` it is still the flag of the package) and `--no-install` does not stop the download. In the other launchers the hook cannot tell the two readings apart and looks both up, marking the command uncertain (a name the registry does not have is a warning, never a deny; a malicious one is denied): a word after a group of letters (`npx -qy false <package>`), after an exact flag of `pnpm dlx`, `yarn dlx` or `bunx` (`bunx --quiet false <package>`), and after a "fetch nothing" or shell-mode flag the word is that flag's value and the next word is looked up (`npx --no false <package>`, `pnpm dlx -c false <package>`). `npx --yes false <package>` still looks up `false`: npx fetches it. `pnpm dlx -c <package>` and `pnpm dlx --shell-mode <package>` look the one word up as the package; with several words in quotes (`-c 'tool --version'`) there is no package. In Yarn and bun a `true` / `false` after `--production` is the value of that flag in Yarn 1 and a package in the others, so the line is read both ways: the manifest is read, and a word AFTER the subcommand is looked up as a package in the commands that name packages (`yarn add`, `bun add`, `bun install`), the command being uncertain. In `yarn install --production <word>` and in a word BEFORE the subcommand (`yarn --production true`, `yarn --production true add <package>`) only the manifest is read and the rest of the line as the subcommand says: no manager measured installs that word as a package. The `-s` of npm is a loglevel shorthand like `-q` and `-d`, so `npm exec -sy true <package>` takes the word as the value of `-y`.

**Initializers.** `npm create|init|innit <x>`, `yarn create <x>`, `pnpm create <x>` and `bun create|c <x>` download `create-<x>` and run it (measured 2026-11-20 with npm 11.19, Yarn 1.22, 3.8 and 4.18, pnpm 11.24 and bun 1.4), so the hook looks that package up as it does for `npm exec create-<x>`: `<x>` is `create-<x>`, `@scope` is `@scope/create`, `@scope/<x>` is `@scope/create-<x>`, with the version, range or tag of the word; the words after it are the initializer's own arguments and are never looked up (a word after a flag the hook does not know is a candidate, as for any launcher). A name the registry does not have is denied for npm, Yarn and pnpm in a plain single statement with only the flags measured for that verb (`-y`, `--yes`, `-q`, `--quiet`, `--silent` for npm; `-q`, `--quiet` for Yarn; none for pnpm), as for `npm exec`; anywhere else it is a warning, and a package OSV lists as malicious is denied. `bun create` only warns, never denies, for a missing name: bun uses a template of that name from a `.bun-create` folder of the project when there is one and then does not ask the registry for `create-<x>` (measured), and the hook does not read that folder. A word that already starts with `create-` is asked as `create-create-<x>` by npm and bun and as `create-<x>` by pnpm; Yarn 1 and 3 and Yarn 4 differ, so both names are looked up and a missing one only warns, as for the bare word `create`, a scope whose name starts with `create-` and `yarn create @scope@<version>` (not measured, or read differently by Yarn 1). Not read: `npm init`, `npm init -y`, `yarn create` and `pnpm create` with no name, which fetch nothing, and an initializer that is not a registry name (`npm init <user>/<repo>`, a path, a URL). `npm install-test <package>` and `npm it <package>` are vetted like `npm install <package>`. The [known limits](hooks-known-limits.md) list the rest.

**Names that end like an archive.** A bare word that ends like an archive (`lodash.zip` is a real package) is a package name for most managers, so it is vetted like any other word. Only the endings a manager reads as a file are skipped (measured with npm 11.20, bun 1.4, pnpm 10.33, Yarn 1.22 and 4.18, pip 26.2, uv 0.13 and poetry 2.5; a word with a version, `lodash.zip@4.2.0`, is vetted too):

- npm and `npx` read `.tgz`, `.tar.gz` and `.tar` as a file, unless the word has a scope (`@s/y.tgz` is a name); bun and `bunx` read the same three as a file, scoped too.
- pnpm and Yarn, with `pnpm dlx` and `yarn dlx`, read no ending as a file: every word is a name.
- pip reads `.zip`, `.whl`, `.tar`, `.tar.gz`, `.tgz`, `.tar.bz2`, `.tbz`, `.tar.xz`, `.txz`, `.tlz`, `.tar.lz` and `.tar.lzma` as a file; uv (`uv add`, `uv pip install`, `uvx`, `uv tool install`) reads `.zip`, `.whl`, `.tgz`, `.tar.gz` and `.tar` as a file; poetry reads eleven, the twelve of pip without `.whl`, as a file.
- **A `>` or `<` glued to a word.** `npm install name@>=1.0.0` without quotes is read as the shell hands it to the manager (measured 2026-11-20): bash gives npm, pnpm, bun and Yarn 1 the word `name@`, which installs the latest, and writes the range to a file named `=1.0.0`; PowerShell 7.6 and 5.1 give the program the whole word, a `>` being a redirection only at the start of a word or after digits or `*`, and `<` never. The hook reads the text before the operator as the word, never the target of the redirection, and with the PowerShell tool also the whole word and the next word as an argument; an npm, pnpm, Yarn or bun range with `<` or `>` is looked up with the range and without it. `name@` is the package `name` with no range. The line stays uncertain: a missing name warns, a malicious package is denied. See `install-redirect-glued-word` in the known limits.
- The name after `npm:` in an alias (`x@npm:evil.zip`) is a name for every manager, whatever it ends in, and the `npm:` prefix is read in any letter case (`x@NPM:evil` is the package `evil`, as npm reads it). That is the alias reading of npm and pnpm, and of every manager when the word has a `@range` of its own (`x@npm:real@1.0.0`). Yarn 4 asks the registry for `x` itself when the word after `npm:` is a version, a range or a tag; bun does so for a full version or a range that starts with an operator, and asks for the word (an alias) for `latest`, `next`, `1`, `1.2`, `1.x` or another word. For `yarn add x@npm:^1` and `bun add x@npm:*` the package is `x`; for a word that is a valid name with no range (`x@npm:latest`, `x@npm:1.0.0`, `x@npm:real`) the hook looks up both `x` (at that version or range, when the word is one) and that word, and counts the command as uncertain, so a name that is missing is a warning, never a deny; a malicious one is denied. A range with an operator is read unquoted too (`x@npm:>=1.0.0`: bash hands the manager `x@npm:`, PowerShell the whole word — see the next paragraph); one with a space needs quotes. A `package.json` value `"x": "npm:1.0.0"` leaves a "could not vet" line at every `yarn install` for the name `1.0.0`, which the public registry answers with a document that is no package. Yarn 2 and 3 were not measured: the reading follows Yarn 4. The version part of `name@x.tgz` is a file only for npm and bun and only when it ends in `.tgz`, `.tar.gz` or `.tar`: it is then not looked up; for every other manager and ending (`evil@foo.zip`, or anything with pnpm or Yarn) it is a tag and the name before the `@` is vetted (and `vet_packages`, which names no manager, always takes it as a tag). The versioned forms of pip, uv, poetry, composer and dotnet are unchanged.
- The part after the `@` of `name@<spec>` that starts with `~` opens a path only when a slash or a backslash follows it (`name@~/x`, `name@~user/x`, `name@~1/x`): that word is not looked up. Any other `~` word is a spec of the registry and the package is vetted: with the range when the hook reads one (`name@~1.0.0`, `name@~1`, `name@~1.0.x`, as with `^1.0.0`), with none when it does not (`name@~x`, `name@~abc`, `name@~latest`, a lone `~`). `~/x` was measured with npm, pnpm and Yarn 1, which ask the registry for nothing; `~user/x` only with npm.
- In a `package.json` a key is always a name. A value is a file only for npm and bun (`.tgz`, `.tar.gz`, `.tar`); for pnpm and Yarn it never is. A dependency is vetted by its name unless its value is positively something else: a path (`./x`, `~/x`, a drive letter), one of the protocols the hook knows (`file:`, `link:`, `workspace:`, `catalog:`, `portal:`, `patch:`, `exec:` and `jsr:`), a URL, a git repository, `user/repo` or such a file. The value is its range when the hook reads one, and no range when it does not (`~x`, `^x`, `> 1`, `~abc`, a value over 100 characters), and another `word:rest` (`foo:^1`) is a spec of the registry too, so a value the hook cannot read is never a way to skip the check. A line of a requirements file follows the list of pip or of `uv pip install`.
- pipx, composer and dotnet were not measured: such a word, whatever ending any measured manager reads as a file (or `.egg`, `.nupkg`), is vetted as a name and the command counts as uncertain, so a name the registry does not have is a warning and never a deny.

When a configured registry explains a missing name, the warning names it by its host and the file or variable that configures it, never by its URL: the registry is shown as `scheme://host`, with no credentials, port, path, query or fragment, and a value that is not a URL with a host (a folder, a share, `no-index`) is not shown at all.

The network hosts involved are listed in [SECURITY.md](../SECURITY.md).

## Configuration

The project is the directory Claude Code names in `CLAUDE_PROJECT_DIR`; without it, the nearest ancestor of the session's working directory that holds `.guardian` or `.git` — never the home directory or one of its ancestors, nor the temp directory itself, where a stray `.guardian` would otherwise become every unmarked project's configuration; failing both, the working directory itself. The project files below are read from there, and paths are made relative to it, wherever the session has `cd`-ed to — from `<project>/packages/api` the project's configuration applies, and a `Write` of `<project>/.guardian/hooks-allowlist.json` is denied as it is from `<project>`. A `.guardian/hooks*.json` at any depth under the project (or under the working directory) is guarded the same way. Every guarded path — these files and Claude Code's settings — is compared as the filesystem opens it: on Windows without an NTFS stream suffix (`hooks.config.json::$DATA` writes the file itself; `:name` and `:name:$DATA` are streams of it) or trailing dots and spaces (`hooks.config.json.`, `.guardian.\…`), and everywhere through an 8.3 short name (`HOOKSC~1.JSO`) or a link, when the path or a directory above it exists. A hard link — the same file under another name, which no path comparison sees — is recognised by device and inode: a `Write` of `notes.json` made with `ln .guardian/hooks.config.json notes.json` is denied as a `Write` of the configuration, and one of a hard link to Claude Code's settings is judged as that settings file. Creating a hard link to a hook configuration file or to Claude Code's settings (`ln` without `-s`, `link`, `cp -l`, `New-Item -ItemType HardLink`, `mklink /H`, `fsutil hardlink create`), or a hard-link copy of a directory that holds them (`cp -al .guardian backup`, and `~/.config/dev-guardian` or `.claude`), is denied too — and so, since 3.4.0, is a symbolic link or a junction to them (the shell guard, above): the `Write` / `Edit` path resolution follows one, but a shell write through it names neither. The shell guard drops the same Windows suffixes from the paths a command writes, and judges each path a command writes, removes or replaces also through the links the same command made before it (`ln -s ~/.config c && echo … > c/dev-guardian/hooks.json`) and — from a hook call — through those already on disk, resolved the way a `Write` path is (a junction `z` to `.claude` makes `echo … > z/settings.local.json` a write of the settings); a write follows a link at the path itself, a remove or a new link only the links above it. Past 64 links in one command, or 64 paths looked up, the command warns "part of this command was not assessed". A written path on the network (`\\host\share\…`, `//host/share/…`, `\\?\UNC\…`) is never asked of the filesystem — a `Write` to an unreachable host held the hook 21 s, past its timeout: an admin share of this machine (`\\localhost\C$\…`, `\\127.0.0.1\…`, `\\[::1]\…`, its own name) is read as the local path it names, and any other share's path is denied when it ends in a hook configuration file (`.guardian/hooks*.json`, `.config/dev-guardian/hooks.json`) or in the registry's default location; an edit of Claude Code's settings there is judged on its own strings, the file unread.

| Where | Who may write it | What it can do |
| --- | --- | --- |
| `.guardian/hooks.config.json` (project) | the user — an assistant's `Write` / `Edit` / `MultiEdit` is denied, and so is a shell write the guard can see (below) | only what makes the guard stricter or is advisory: `enabled: true`, `bash.block: true`, `bash.warn: true`, `secrets.block`, `secrets.warn`, `sessionStart`, `ignorePaths`. `"enabled": false`, `"bash": { "block": false }` and `"bash": { "warn": false }` here are **ignored**, and SessionStart says so; there is no project-level switch for package vetting. |
| `~/.config/dev-guardian/hooks.json` (user) | the user — an assistant's `Write` / `Edit` / `MultiEdit` is denied, and so is a shell write the guard can see (below) | every key, winning over the project file: `"enabled": false` turns every hook off, `"bash": { "block": false }` turns the shell block into a warning |
| `.guardian/hooks-allowlist.json` (project) | the user — an assistant's `Write` / `Edit` / `MultiEdit` is denied, and so is a shell write the guard can see (below) | substrings that silence a secret warning (and exempt a match from the opt-in secret block when the project itself enabled it): a JSON array, or `{ "secrets": [...] }`. Advisory, like `secrets.warn`. An entry under four non-blank characters, which nearly every line would hold, is ignored, and SessionStart names it. |
| `GUARDIAN_HOOKS=off` | environment | disables every hook — SessionStart still leaves [the session mark](#the-session-mark), which says so |
| `GUARDIAN_HOOKS_BASH_BLOCK=0` / `1` | environment | forces the shell block off or on, over both files |
| `GUARDIAN_PKG_VET=0` | environment | disables package vetting only |
| `GUARDIAN_PKG_VET_DEADLINE_MS` | environment | package vetting's deadline for one hook call, in ms from its start (default 8000, at least 3000, at most 12000) |

`ignorePaths` defaults to `/test/fixtures/`, `eval-vuln-fixture`, `/.guardian/` and `__fixtures__`, matched against the path relative to the project. An entry every path (or nearly every one) holds — `""`, `"/"`, which begins every project-relative path, or `"."`, which every name with an extension holds — silences every secret warning, and SessionStart says so. The plugin's own directory is always skipped. The user-level `ignorePaths`, when set, replaces the project's. A project's `ignorePaths` narrows the secret **warning** only: it never exempts a path from a `secrets.block: true` set in the user-level config, which honours the user's own `ignorePaths` or the defaults. (A block the project itself enabled may be narrowed by the same project's list.) The project's `.guardian/hooks-allowlist.json` follows the same rule: it silences the warning, and it exempts a match from the block only when the project itself enabled that block — never from one the user enabled.

Each setting is read only when it has the type above — a boolean, an object for `secrets` and `bash`, a list of strings for `ignorePaths` — in either file. One of another type is left out, its default applies, and SessionStart names it with its file (`in ~/.config/dev-guardian/hooks.json, "ignorePaths" was ignored (not of the type the hooks read)`). Until 3.4.0 a user-level `"ignorePaths": "/"` broke the check every write makes, so the hook gave no secret warning at all, and `"enabled": "no"` counted as on.

**How the configuration files are read.** Each one — the project config, the allowlist and the user-level config — goes through two checks, and a file that fails either is not read, counts as absent (the protective defaults), and is named by SessionStart; a file that is not valid JSON is named too.

1. **Before anything is opened**, every path component below the project directory (for the two project files) or the home directory (for the user-level file) is examined with `lstat` and `readlink`, which never follow a link and never touch its target. If a link on the way — the file itself, `.guardian`, `.config`, `dev-guardian`, or any local link one of them leads to — points at a UNC or device path (`\\host\share`, `//host/share`, `\\?\…`, `\\.\…`), the file is refused. Opening such a link can wait on the network for minutes (≈136 s was measured on Windows for an unreachable host), far past the hook's 15 s.
2. **Then the file is opened** (a link is followed; on Linux and macOS with `O_NONBLOCK`, so a FIFO opens at once instead of waiting for a writer), and what was OPENED is checked with `fstat`: only a regular file of at most 64 KiB is read, and no more than 64 KiB + 1 bytes are read from it, so a file that grows after the check is refused too. A FIFO, a link to `/dev/zero`, a Windows link to a named pipe (which `stat`s as an empty regular file), a larger file or a file this account may not read is refused on its descriptor and closed unread; a directory is refused too (Windows will not open one at all). Because these checks apply to the open descriptor rather than to the path, swapping the path for a FIFO between two checks changes nothing. A leading UTF-8 byte-order mark is stripped.

A FIFO there used to hang the hook until Claude Code killed it at 15 s, after which the tool call ran unguarded. **Not covered:** the project and home directories themselves and their ancestors (the user's own layout), and a path the operating system redirects to the network without a link — a mapped drive letter, a DFS namespace, an NFS or SMB mount — which is opened like any local path. The install hook reads registry configuration (`.npmrc`, `package.json`, `pip.conf`, `nuget.config`, …) through both checks too, capped at 1 MiB: the walk runs below the project for a file in it, from the file's own directory for one in a parent of the project, below the home directory for a user file and from the filesystem root for a system file — never over the project or home directory themselves or their parents. A refused file counts as possibly naming a private registry (above).

**Shell writes.** The shell guard judges what a command does to the three files, command by command — never their content, so reading them (`cat`, `cp` from them, `sed -n`, `grep`) stays allowed:

- **writing one** — a redirection (`>`, `>>`, `>|`, `N>`, `&>`), `tee`, `sed -i`, `perl -pi` / `ruby -pi`, `sort -o`, `truncate`, `sponge`, `shred`, `dd of=`, `curl -o`, `wget -O`, `ed`, `ex`, `vi` / `vim` / `nvim` (`vim -es -c … -c wq`), `cp` / `mv` / `install` / `rsync` onto it (or into its directory under its name, a glob — in its name or in a directory above it, `~/.config/dev-guardia?/hooks.json` — or a brace that can name it included), a rename onto it, PowerShell `Set-Content` (and Windows PowerShell's `sc`), `Add-Content`, `Clear-Content`, `Out-File`, `Tee-Object`, `New-Item -ItemType File`, `Copy-Item` / `Move-Item` / `Rename-Item`, `[IO.File]::WriteAllText` and the other `[IO.File]::` writes, a `[IO.StreamWriter]` or a writing `[IO.FileStream]` opened on it (`::new(…)`, `New-Object …`), and cmd `copy` / `move` / `ren` / `>`;
- **removing one** — `rm`, `unlink`, `del`, `erase`, `Remove-Item`, `[IO.File]::Delete`, a `mv` or rename that moves it away — and removing `~/.config/dev-guardian` itself;
- **replacing a configuration directory** — a directory moved or copied onto `.guardian` or `~/.config/dev-guardian` (`mv`, `cp -r` / `-a`, `rsync -a`, `Copy-Item -Recurse`, `Move-Item`, `xcopy`, `robocopy`), which becomes the directory when it did not exist.

A relative path is resolved against the `cd`, `pushd` or `Set-Location` earlier in the same command (`cd ~/.config/dev-guardian && echo … > hooks.json`) — back through `cd -`, `cd "$OLDPWD"` and `popd`, and through a `CDPATH` the command sets (`CDPATH=~/.config cd dev-guardian`) — and every command of a quoted `cmd /c "…"` line is judged the same way, its `cd /d` and `>` included. From a hook call, which knows the project and the working directory, a path spelled in full that lies outside both and the home directory only warns: a project's `.guardian/hooks*.json` counts under the project or the working directory, the user-level `hooks.json` only as the home directory's own, Claude Code's settings under any of them (or `CLAUDE_CONFIG_DIR`); a relative path, a variable or a glob counts as this session's. `check --bash` knows neither, and denies them all. Scripts a command hands a shell (`bash -c`, `eval`, `pwsh -Command`, `-EncodedCommand`) are judged as commands. Program text on the command line — `node -e`, `tsx -e`, `ts-node -e`, `python -c`, `perl -e`, `ruby -e`, `php -r`, `deno eval`, `pwsh -Command`, also behind `npx`, `bunx`, `pnpm dlx` / `exec`, `npm exec`, `yarn dlx` / `exec`, `bun x`, `uv run` and cmd's `start`, and a program fed to `python` / `node` through a heredoc or `echo … |` — cannot be judged that way, so it is denied when one of its string literals names a hook configuration path at all, reading or writing (reading one needs no program): a literal ending in the path, or the parts of one (`join(home, '.config', 'dev-guardian', 'hooks.json')`); a sentence that merely mentions it is not.

**Claude Code's own settings.** A `.claude/settings.json` or `.claude/settings.local.json` (project or user level) — and, when Claude Code runs with `CLAUDE_CONFIG_DIR`, the `settings.json` / `settings.local.json` directly in that directory, which are then the user's settings; and the machine's managed settings, which win over every other file (`managed-settings.json` in `ClaudeCode` under Program Files or ProgramData on Windows, in `/Library/Application Support/ClaudeCode` on macOS, in `/etc/claude-code` elsewhere) — with `"disableAllHooks"` set to anything that may read as true (`true`, `"true"`, `1`, even `"false"`), an `env` block setting `GUARDIAN_HOOKS=off`, `GUARDIAN_HOOKS_BASH_BLOCK=0` / `false`, `GUARDIAN_PKG_VET=0`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, or — to any value — `NODE_OPTIONS` (it runs code in every hook before the hook starts: `--import=data:…,process.exit(0)` made the dispatcher silent on `rm -rf /`), `GUARDIAN_PKG_VET_DEADLINE_MS` or `GUARDIAN_OFFLINE`, or an `enabledPlugins` entry naming dev-guardian set to anything but `true` (`false`, `"false"`, `0`), switches the hooks off. Which value forms Claude Code honours is its parser's business, so an ambiguous one counts; the file is read as JSONC (comments, trailing commas), a key's escapes are decoded (`"disable\u0041llHooks"`), a key that repeats counts every time it appears, and JSON nested deeper than that reader goes (64 levels) is read by `JSON.parse`. Each side of an edit is read once, and a reading that takes longer than 4 s is **asked about**. An assistant's `Write` / `Edit` / `MultiEdit` of those files is denied when its **result** sets one of those that the file did not already set; every other edit — permissions, other environment variables, other hooks, other plugins, and any edit of a file where the user already set such a key (with that value) — goes through, except that these are **asked about**: a new `env` `PATH`, `HOME` or `USERPROFILE` — which decide the `node` every hook entry starts and the home its user configuration is read from — and any other new `NODE_*` or `GUARDIAN_*` variable or proxy (`NODE_EXTRA_CA_CERTS`, `NODE_USE_ENV_PROXY`, `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`), whose effect on the hooks is not known here — not `NODE_ENV`, nor a known switch at a harmless value (`GUARDIAN_PKG_VET=1`); and an `Edit` of an existing file that cannot be applied as plain text (its `old_string` not found). An MCP write tool's change of those files whose result cannot be worked out — Serena's `replace_regex`, an edit matched as a regular expression, a glob or ignoring case (a flag nested in an options object or spelled as a string included: `{options: {useRegex: true}}`, `isRegex: "true"`, `flags: "i"`, `mode: "regex"`), a move or copy of a prepared file onto them, arguments no known key names — is **asked about**: Claude Code asks the user (denied outright when its own strings name such a setting). So is an MCP tool that deletes those files or moves them away (`delete_file`, `remove_file`, `move_file` with them as the source), which drops every `permissions.deny` rule they hold; a copy of them is only a read. So is a shell command that deletes them or moves them away (`rm`, `mv`, `Remove-Item`, `del`, … — [the shell guard](#the-shell-guard)). `{"disableAllHooksX": true}` written, then `X"` replaced by `"`, switched the hooks off in two steps that each passed. A shell write of those files (a redirection, `mv tmp .claude/settings.json`, `jq … | sponge`, `sed -i`, program text naming the file) cannot be read reliably, so it is judged by the command's text: it is denied when the command names `disableAllHooks`, `GUARDIAN_HOOKS`, `GUARDIAN_HOOKS_BASH_BLOCK`, `GUARDIAN_PKG_VET`, `GUARDIAN_PKG_VET_DEADLINE_MS`, `NODE_OPTIONS`, or `enabledPlugins` together with `dev-guardian` — also spelled through an escape (`disableAllHook\x73`, `s`, octal) or inside a base64 literal the command holds (`echo eyJ… | base64 -d > .claude/settings.local.json`); `jq '.permissions…' … > tmp && mv tmp .claude/settings.json` goes through. The shell rule matches the key's **name**, whatever the value, so it also denies writes that do not loosen anything: setting `GUARDIAN_HOOKS_BASH_BLOCK` to `1`, `"disableAllHooks": false`, deleting such a key (`jq 'del(.disableAllHooks)'`), or `"dev-guardian@…": true` in `enabledPlugins` — make those edits with `Write` / `Edit`, which judge the result. `claude plugin disable`, `uninstall` or `marketplace remove` naming dev-guardian is denied too.

### The database registry

`db adopt --yes` (`node "<plugin root>/cli/dev-guardian.mjs" db adopt --project <dir> --yes` — a plugin install puts no `dev-guardian` on PATH) makes a project's database trusted by writing an entry into dev-guardian's registry, `<data dir>/registry/<db_id>.json`. The data directory is `GUARDIAN_DATA_DIR` when set; otherwise `%LOCALAPPDATA%\dev-guardian` on Windows, `$XDG_DATA_HOME/dev-guardian` (an absolute one) or `~/.local/share/dev-guardian` elsewhere. Which database to trust is the user's decision, so the registry is guarded the way the hook configuration is:

- an assistant's `Write` / `Edit` / `MultiEdit` / `NotebookEdit` (or an MCP write tool's call) of the registry or anything in it is denied, the deny naming the runnable `db adopt` line for the user — the path compared as the filesystem opens it (NTFS stream suffixes, trailing dots and spaces, 8.3 names, links), and a hard link to an entry recognised by device and inode;
- a shell write into it is denied: a redirection, `tee`, `cp` / `mv` / `install` / `rsync` into it, `Set-Content`, `Copy-Item`, `Out-File`, `[IO.File]::WriteAllText`, cmd `copy`, a link created in it or at it, a hard link to an entry, the registry or the whole data directory replaced by a directory moved or copied onto it, and program text that names it — in its actual location and in the spellings of the defaults (`~/.local/share/dev-guardian`, `%LOCALAPPDATA%\dev-guardian`, `$env:LOCALAPPDATA`, `$XDG_DATA_HOME`, `$GUARDIAN_DATA_DIR`), a `cd` there included.

Reading the registry and removing an entry — which only un-trusts a database — stay allowed; so does the rest of the data directory. A program that writes the registry by its own means (a script run from disk, a path built at run time) is not seen, as for the hook configuration.

**Known limits.** What the guards do not cover is listed in [hooks-known-limits.md](hooks-known-limits.md): the ways to change what the hooks do that are not refused — switching the guardrails off stays the user's decision —, what the shell guard, the write guards and the secret scan do not see, and the size and time limits. That page is generated from `mcp/test/fixtures/hooks/known-limits.yml`, where each limit carries examples a test runs against the real detector or dispatcher, so it states what the guards answer today.

## The same detectors from a terminal

```text
node cli/dev-guardian.mjs check --file path/to/file      # secrets, exit 1 on a finding
node cli/dev-guardian.mjs check --bash "rm -rf /"         # ok / warn / block, exit 1 unless ok
node cli/dev-guardian.mjs check --bash 'Remove-Item "C:\Users\" -Recurse' --powershell   # as the PowerShell tool
node cli/dev-guardian.mjs check --file .env --min high --json
```

Exit code 3 is a usage error — neither or both of `--file` and `--bash`, an unknown argument, a `--min` other than `high` or `medium` — or an unreadable `--file` (2 before 3.3.0, as for every command). A file is read as UTF-16 when it starts with a UTF-16 byte-order mark or its bytes are NUL-interleaved (what PowerShell 5.1's `>` and `Out-File` write), as UTF-8 otherwise.
